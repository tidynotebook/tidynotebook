# Security policy

## The two editions

This policy covers both editions of tidy notebook. They run the same code, so
report a problem of the code once.

- **tidy notebook self-hosted** is the edition that you run on your own
  server. The person who runs the server is its operator.
- **tidy notebook cloud** is the paid service of the owner at
  `app.tidynotebook.com`. The owner is its operator. It runs the public image
  of a public release with no change.

## Report a problem privately

Do not open a public issue, a public discussion, or a pull request for a
security problem.

1. Open the GitHub **Security** tab of this repository.
2. Select **Report a vulnerability**. This opens a private advisory. The owner
   and the people who help with the advisory can read it.
3. If private reporting is not available, send the report to
   [hello@bhushankhanale.com](mailto:hello@bhushankhanale.com).

Include these items in your report:

- What the problem lets an attacker do.
- The steps to reproduce it, or a short proof.
- The edition. For tidy notebook self-hosted, add the version, commit, or image
  tag you tested.
- Your deployment shape, for example the reverse proxy in front of the app.

### What to expect

The owner acknowledges a report and states whether it is accepted or refused.
tidy notebook is a one-person project, so there is no service level agreement.
Please give the owner reasonable time to release a fix before you publish.

## Supported versions

Only the newest release and the `main` branch get fixes. There is no long-term
support branch.

- **tidy notebook cloud** gets a fix when the owner deploys the release that
  holds it.
- **tidy notebook self-hosted** gets a fix when the operator installs that
  release.

## Trust model

Read [the security model](docs/guide/security-model.md) before you decide what
is a vulnerability. In short:

- The server operator can read every note.
- Each account has its own notes.
- Disk encryption and HTTPS are the operator's job.

## In scope

- Reading, changing or deleting notes, attachments or history without a valid
  session or API key.
- Reading or changing the notes of another account.
- Creating an account outside the setup, invitation or sign-up rules.
- Cross-site scripting through note content, an attachment, a diagram or a
  rendered link.
- Cross-site request forgery, session fixation, or a cookie that leaves its
  origin.
- Escaping the row level security of the database with the runtime role.
- Reading note text, search text, credentials or tokens from a log, an error
  message or a metrics answer.
- A path traversal or an unchecked file type in the attachment store.
- A dependency with a known exploitable vulnerability that this product
  reaches.
- A default in `docker-compose.yml` or `.env.example` that exposes an
  installation.
- Bypassing account limits or the operator API token check.

A report about the cloud billing service uses the same private contact. The
billing service is a separate program. This repository holds the core.

## Out of scope

- The operator reading the notes of their own installation.
- An attack that needs the operator's host account, database credentials, or
  physical access.
- A missing HTTPS header on an installation that has no reverse proxy in front
  of it.
- A person who deliberately stops their own installation. An account that
  stops service for other accounts is in scope.
- A report generated by a scanner with no proof that the product reaches the
  code.
- Social engineering of the repository owner.
- A load test, a denial of service, or an automated scan against tidy notebook
  cloud. Test on an installation of your own.
